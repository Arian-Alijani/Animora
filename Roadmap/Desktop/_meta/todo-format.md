# TODO.md Format

The exact structure Step 0 must produce for `phases/NN-name/TODO.md`. Kept rigid so every phase's
list looks the same and costs the same to parse for an AI session.

```markdown
# TODO — Phase NN: <Phase Name>

Generated by Step 0 on <date>. Source: PHASE.md Scope + <list the exact docs Step 0 read>.

- [ ] 1. <Imperative, specific action, one deliverable> (<rule IDs it satisfies, if any>)
- [ ] 2. <...>
- [ ] 3. <...>
...
- [ ] N. Verify phase Completion Criteria (see PHASE.md) and update PROGRESS.md to `complete`
```

## Rules

- **Numbering**: sequential, stable once written. If a later session finds a missing step, append
  it at the end with the next number rather than renumbering (renumbering breaks resume-by-checkbox
  continuity across sessions).
- **Granularity**: each item should be completable and commit-able on its own. If an item feels like
  it needs its own sub-checklist, it is really 2-3 items — split it before saving.
- **Citations, not explanations**: an item may end with `(DT-04, DESK-ARCH-09)` — it must never
  contain a paragraph re-explaining what those IDs mean (CM-02).
- **No implementation detail beyond the "what"**: Step 0 names the deliverable (e.g., "Add
  `OwnerListViewModel` with keyset-paginated search binding") — it does not pre-write code, class
  bodies, or XAML in the TODO file itself. That is the implementing session's job.
- **Ask-first items**: if a business rule is ambiguous, the item reads
  `- [ ] N. Ask the user: <question>` and every later item that depends on the answer says so
  explicitly (`(depends on item N's answer)`).
- **Final item is always the completion-criteria check**: this is what lets `PROGRESS.md` be updated
  to `complete` with confidence instead of by assumption.
- **Do not restate PHASE.md**: TODO.md assumes PHASE.md is read first; it does not re-paste the
  Goal/Scope.
