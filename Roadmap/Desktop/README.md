# Desktop Roadmap — Animora

Entry point for AI-driven implementation of the Avalonia desktop client (P1, see repo-root
[`AGENTS.md`](../../AGENTS.md) §1). This roadmap is a planning artifact, not an architecture doc: it
never restates a rule, it only sequences work and cites the doc/ID that owns each rule (INV-18).

Read this file once per new session before opening any phase. Then read
[`_meta/session-protocol.md`](_meta/session-protocol.md) for the exact resume/execute procedure.

## Build order and why UI comes first

Per the objective set for this roadmap, desktop implementation is split into two stages so the
complete interface can be designed, reviewed, and refined before deeper layers are built — without
ever producing throwaway code or violating layering:

- **Stage A — Interface (phases 00-13)**: solution skeleton, design system, shell/navigation, the
  minimal shared primitives, then every module's screens, ending in a consolidation/review gate.
  Screens are built inside their **final** architectural boundaries (DT-01/DT-02/DT-09,
  [12-desktop-architecture.md](../../docs/architecture/12-desktop-architecture.md)): ViewModels
  dispatch `Mediator` requests to real `Handlers/` in the module project, exactly as they will in
  production. The only thing deferred is *where a handler gets its data from* — see "the data
  seam" below. No ViewModel ever touches `DbContext`/`HttpClient` at any stage (DT-02), so nothing
  built in Stage A is thrown away in Stage C.
- **Stage B — Gate (phase 13)**: a single consolidation phase where every screen is reviewed as a
  whole (navigation, RTL, tokens) before persistence work begins.
- **Stage C — Local data platform (phases 14-23)**: SQLite/SQLCipher/EF Core/Dapper foundation,
  then one phase per module that swaps the Stage A data seam for real local persistence. Handlers,
  ViewModels, and Views do not change shape in this stage — only the concrete data-access
  implementation behind each module's own interface changes (DIR-03's spirit applied to desktop).
- **Stage D — Cross-cutting depth (phases 24-30)**: documents/printing, barcode/imaging, the local
  job scheduler, native notifications/update seam, security hardening, performance budget, backup
  UX — capabilities that cut across modules and are cheapest to build once the module screens and
  their data exist.
- **Final phase (31)**: release readiness — the gate that gates P2 (AGENTS.md AG-01/AG-04: no P2/P3
  work starts until this signs off).

### The Stage A/C data seam (read before any module UI phase)

Each module project (`Animora.Desktop.Modules.X`) defines its own read/write interfaces for the
data its handlers need (mirrors DIR-03's "modules reference infrastructure only through interfaces
they define"). In Stage A, composition wires an in-memory/design-time implementation of those
interfaces so every screen is fully click-through and demoable with realistic sample data. In Stage
C, composition is repointed to the real `Animora.Desktop.Data` (EF Core writes / Dapper reads)
implementation. Interfaces, `Handlers/`, `ViewModels/`, and `Views/` do not change between the two
stages — this is what makes Stage C "add business logic," not "restructure the project." Phase
`02-shell-and-navigation` establishes this pattern once; every module UI phase and its paired local
data phase reference it instead of re-describing it (INV-18).

## Working through a phase (every session)

1. Open [`PROGRESS.md`](PROGRESS.md). Find the first phase whose status is not `complete`.
2. Open that phase's `phases/<NN-name>/PHASE.md`.
3. If `TODO.md` does not exist yet in that folder: run **Step 0** for this phase per
   [`_meta/session-protocol.md`](_meta/session-protocol.md) — it reads the phase's Goal/Scope/Key
   References plus the cited architecture docs and generates `TODO.md`. Update `PROGRESS.md` to
   `todo-ready`.
4. If `TODO.md` exists: implement the next unchecked item(s). One session may complete one item or
   many — both are expected and supported.
5. Check off completed items in `TODO.md`; update `PROGRESS.md`'s counter and status
   (`todo-ready` -> `in-progress` -> `complete`) for that phase only.
6. Commit per the repo-root workflow (AGENTS.md §8) with the phase/module in the commit scope.

Never open another phase's `TODO.md` to work on the current one; never open `backend/` or `web/`
while any Desktop phase is active (AG-01, AG-05).

## Non-negotiables inherited from the project (not restated here)

Every phase and every TODO Step 0 generates MUST obey repo-root `AGENTS.md`, `ARCHITECTURE.md`'s 10
invariants, `docs/TECH_STACK.md`, and `desktop/AGENTS.md`'s DT-01..DT-12. This roadmap sequences
work; it never overrides or duplicates those rules. If a phase seems to require violating one, stop
and flag it in `docs/architecture/_meta/open-questions.md` (AG-10) instead of working around it.
